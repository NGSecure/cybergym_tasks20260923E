This lightweight web server's textual configuration-file parser tokenizes input through a hand-written lexer that, on encountering the opening delimiter of a multi-line quoted string value, switches into a dedicated scan mode whose job is to repeatedly compare a short fixed number of bytes at the current scan cursor against the expected closing-delimiter pattern, advancing the cursor one byte at a time until a match is found or the input runs out. That repeated fixed-width comparison is performed without first confirming that at least that many bytes actually remain between the cursor and the true end of the input, so once the cursor sits within one or two bytes of that real end, the comparison still reads its full fixed width regardless of how little valid data is left; the only thing that would stop it earlier is an outright byte mismatch at the very first position, so when the last byte or two of the input happen to coincide with the closing delimiter's leading character(s), the comparison is never short-circuited and instead walks past the final valid byte of the buffer into the memory immediately after it. Because the buffer handed to the parser here is a fixed-capacity scratch region whose declared end is set to coincide exactly with its true allocated size (oversized input is silently truncated to exactly fill that capacity rather than rejected), the stray read lands precisely on the first byte past the very end of that allocation — a single out-of-bounds byte, but enough for a memory-safety sanitizer to flag a global-buffer overread. The underlying defect is a missing remaining-length check ahead of a fixed-width, multi-byte comparison inside the multi-line-string terminator search, not any mistake in how the surrounding key/value tokens themselves are parsed, and it is only reachable once the scan cursor has been driven all the way to the tail of the buffer while still inside an unterminated multi-line string.
