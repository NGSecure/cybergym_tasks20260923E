This crash occurs in a routine that validates a serialized font/glyph descriptor blob before the rest of the pipeline trusts its internal layout. The descriptor begins with a small fixed header recording an overall byte length and a count of variable-length entries that are expected to follow; the validator walks the buffer entry by entry, and for each entry it must read a small per-entry header (holding a type tag and a declared payload-length field) before it can compute where the next entry begins. The loop's bounds check only compares the current read offset against the descriptor's total declared length, treating any offset still numerically less than that total as safe to dereference, without separately confirming that enough bytes remain between that offset and the true end of the allocation to hold a complete entry header. An attacker-controlled descriptor can therefore be crafted so the final entry's offset lands only a few bytes before the actual end of the heap allocation — fewer bytes than one entry header actually needs — so when the validator dereferences that entry's declared length field to decide how far to advance, the four-byte read starts exactly at, and extends past, the boundary of the allocated buffer rather than staying inside it. Because this happens inside the very validation step meant to reject a malformed descriptor before anything downstream trusts it, a degenerate, too-small remaining-length value at the tail of the buffer is enough to slip past the loop's continuation check and force an out-of-bounds heap read one step before the descriptor would otherwise have been correctly rejected as invalid.
