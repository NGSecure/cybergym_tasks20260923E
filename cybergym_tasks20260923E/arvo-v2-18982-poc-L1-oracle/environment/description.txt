A PKCS#15-style smart-card emulation layer for CoolKey-brand cards builds an in-memory list of on-card "objects" during card setup, each entry carrying an identifier and (once its payload is later fetched on demand) a heap buffer holding that payload; nothing in the enumeration step that populates this list rejects a second entry from being registered under an identifier the list already contains, so a card that answers the enumeration commands with a repeated identifier ends up with two distinct list entries sharing one id. Enumeration itself has two independent card-side paths, and only when the simpler of the two was not used does setup go on to issue one further card read for a fixed-size manufacturer/identity record used to derive the card's serial number and label; the code checks whether that low-level exchange failed outright, but not whether the card actually returned as many bytes as the fixed-size record requires, so a short reply is still accepted as a full, successful read. Only after that final read is accepted does setup commit the object list built so far as the card's live working state and report overall success — if the read is instead correctly rejected, whatever list had been built is torn down right there, once, before ever becoming live. When the final read is wrongly accepted despite being truncated, a list that already contains a duplicate-identifier pair goes live anyway, and when higher-level code later resolves one of these objects by identifier to lazily fetch and cache its payload, an identifier-keyed lookup performed as part of that fetch can land on the *other* entry sharing the same id rather than the one actually being filled, so the freshly allocated payload buffer's pointer gets written into two separate list entries instead of one. On card teardown, the code walks the full object list and releases every entry's payload buffer unconditionally; because two entries now reference the identical allocation, that one buffer is released a second time.
