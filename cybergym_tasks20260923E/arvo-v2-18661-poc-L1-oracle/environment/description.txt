This is a one-byte heap out-of-bounds read that happens while the driver is building PKCS#15 object emulation for a security-token vendor's smart-card format, specifically while decoding one of that object's fixed numeric attributes (such as its class code) out of a cached, fully-retrieved on-card object record. The object's raw bytes are cached the first time the object is touched in a heap buffer sized to exactly whatever total length the card asserted for that object, and are then walked as a sequence of self-describing attribute entries: each entry carries a small fixed header followed by a length field and payload, and the driver supports two historical encodings of this per-entry layout, distinguished by a marker in the object's own bytes. For the older of the two encodings, the routine that extracts a given attribute's value trusts the length field embedded in that entry at face value: it only verifies that the entry's small fixed header itself still fits within whatever bytes remain in the cached buffer, but never re-checks that the payload length the entry claims -- four bytes, for a numeric attribute -- actually still fits in whatever remains after that header before handing back a value pointer and that claimed length. When such an entry happens to sit close to the very end of the cached object buffer, with only three genuine bytes trailing its header instead of the four the entry claims, this omission alone would already be enough to expose stale or out-of-bounds bytes to the caller. What turns it into an out-of-bounds read is a second, independent check one layer up, where an attribute value is converted into a plain numeric field: that check is written so it only rejects the value when the attribute's declared type looks wrong AND its declared length differs from the expected numeric size, instead of rejecting when either condition alone looks wrong. Because the truncated entry's claimed length is exactly right even though the true remaining bytes are not, this check is satisfied, and the generic big-endian numeric decoder underneath it unconditionally reads four fixed byte offsets from the pointer it was given, walking exactly one byte past the end of the cached allocation on the last of those four reads. Every quantity involved -- the object's overall cached size, which of the two entry encodings is in play, and the individual entry's claimed payload length -- comes directly from bytes the card supplied during ordinary object retrieval and attribute enumeration, so a card (or anything able to substitute a card's responses) that returns an object whose older-style attribute list is truncated by even a few bytes relative to what one of its own numeric-attribute length fields promises can reach this exact one-byte overread through the normal card-initialization sequence, without needing to manufacture any state beyond the bytes it is already trusted to supply.
