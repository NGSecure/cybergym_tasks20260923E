While subsetting a chained contextual rule, the subsetting logic re-validates the rule's trailing backtracking, input, and lookahead glyph-id lists against the retained glyph set before copying the rule forward, and to find the second and third of these variable-length lists it uses a position fixed by the record's compile-time layout rather than one derived by walking forward from the first list's actual, data-dependent length. For this input the resulting table geometry pushes that miscomputed starting position all the way past the end of the small heap allocation holding the font table before any entry is even reached: the very first thing the validation step tries to read at the wrong position -- the two-byte count that is supposed to say how many glyph-id entries the list holds -- already sits outside the buffer, so the out-of-bounds read fires while merely constructing an iterable view over the (mislocated) list, rather than partway through inspecting its individual entries. The read is still a plain two-byte fetch, but here it is the list's own length field, not one of its glyph-id values, that falls off the end of the allocation.
