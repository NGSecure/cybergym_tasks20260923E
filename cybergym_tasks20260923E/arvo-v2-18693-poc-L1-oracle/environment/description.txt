This crash occurs in the file-selection security-attribute parser belonging to one particular smart-card driver's card-type family (a different driver family from the CoolKey/CAC1 one, distinct code entirely), the routine that driver invokes right after an ordinary SELECT FILE exchange completes, to interpret the short list of variable-length access-condition sub-records the card just returned in the file's control data. Each sub-record opens with a one-byte header whose low nibble states that sub-record's own length in bytes, and the parser is meant to use this length -- together with a running position/remaining-length pair -- to know exactly how much of the small heap buffer still belongs to the current sub-record before it may advance to the next one. For one style of sub-record, the code separately derives a "how many PIN-related bytes remain in this sub-record" count by subtracting one from that same length field, implicitly assuming the length is always at least one; it never special-cases the header instead encoding a length of exactly zero, a degenerate but syntactically well-formed sub-record. When the length is zero, that subtraction executes in an unsigned type and wraps around to an enormous value before being narrowed down into the ordinary signed counter the rest of the function consults, leaving this piece of the sub-record's bookkeeping badly out of sync with the sub-record's true (empty) size. Despite that, the parser still goes on -- unconditionally, without first re-deriving how much of the buffer this particular sub-record genuinely still owns -- to pull a further command-selector byte that a normal, non-degenerate sub-record would have room for but a zero-length one does not; because nothing re-validates the position/remaining-length pair against the corrupted count before that byte is fetched, the read walks past the true end of the small allocation and faults, which is why the crash is a wild read rather than a write. Reaching this code needs nothing beyond an ordinary card-enumeration and PKCS#15-binding sequence -- the same repeated per-file SELECT walk of a card's on-card application directory that any normal login or certificate-listing operation performs -- so the vulnerable parser is exercised on the raw, attacker-controlled bytes that any inserted card claiming this driver's card type returns from a plain SELECT FILE response; a noncompliant, corrupted, or actively malicious card need only place one such degenerate, zero-length access-condition sub-record among the otherwise-ordinary ones in a file's security attributes, with no fuzz-harness-only setup or unusual API sequence required to trigger it.
