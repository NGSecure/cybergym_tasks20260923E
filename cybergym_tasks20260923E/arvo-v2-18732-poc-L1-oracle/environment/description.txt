Here the entry point is the narrow, PDF-independent image-decode-only path: a single JPEG-compressed image is fed straight into the library's JPEG-decoding filter with no surrounding document structure at all, and the input is otherwise well-formed rather than truncated or reconstructed -- the difference from the document-rewriting cases is that this file carries a color-transform marker whose declared value falls completely outside the small set of values the decoder actually recognizes as meaningful (an out-of-range code, not simply "none"/"YCbCr"/"YCCK"). Rather than rejecting or normalizing that out-of-range value, the decoder still ends up selecting the four-component conversion routine that is meant only for genuine Adobe-tagged CMYK-style images, and it does so on the very first output row produced right after color upsampling -- i.e. the flagged read happens immediately, inline, during the normal decode/convert loop itself, not in some later buffering or re-serialization stage. What gets read as not-yet-written is one of the four per-pixel component values feeding that conversion, consistent with the decoder having chosen a component layout/interpretation that does not actually match how many meaningful components were produced for that image.
