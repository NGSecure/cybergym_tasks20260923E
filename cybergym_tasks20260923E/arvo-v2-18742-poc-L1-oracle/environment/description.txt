This crash sits in the same TLS certificate-fingerprint reassembly logic used elsewhere in nDPI and shares its root cause: an outstanding-byte counter carried between packets can be corrupted by an unsigned-arithmetic underflow when a new packet's payload turns out to be shorter than the offset the code expected to resume from, so a bogus, inflated byte count reaches nDPI's generic incremental hashing helper instead of the real number of usable bytes. What matters here is the input shape and where exactly the overread lands: this proof of concept supplies enough leading bytes that the hashing helper's first internal block-fill copy stays safely inside the buffer, so processing advances past that initial step into its steady-state loop, which walks the caller-supplied data in successive fixed-size chunks and feeds each one to the underlying block-compression step without re-deriving how many genuine bytes remain. Because the trusted byte count is still the inflated one from the underflowed subtraction, the loop believes another full chunk is available immediately after the point where the real payload ends, and the block-compression step's own internal copy — which unconditionally reads a fixed span for every chunk it is asked to process — steps one byte past the end of the underlying heap allocation while pulling in that chunk.
