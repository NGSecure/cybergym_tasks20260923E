The crash surfaces while the library is only probing a camera raw image well enough to identify it, walking a TIFF-style container down through nested EXIF metadata until it recognizes, from the maker/model strings recorded earlier in the same file, that it is looking at a particular vendor's proprietary sub-block; that recognition alone, with no further validation, is enough to hand control to a dedicated parser for that vendor's obfuscated metadata format. That parser first reads a small directory of entries from the start of the block: a 16-bit entry count taken directly from the file, followed by a step that multiplies the entry count by a fixed per-entry byte width and adds it to a running position within the block to locate the next sub-section. The entry count is stored in a signed 16-bit variable, and while the code does check that this count is not implausibly large, it never checks that the raw value could not have been low enough in the file's encoding to read back as negative once reinterpreted as signed -- so a crafted count near the top of the unsigned 16-bit range becomes a large negative number after that reinterpretation. Multiplying a large negative count by the fixed per-entry width and adding it to the running position then produces a computed position that is deeply negative rather than merely out of range on the high side. The one bounds check guarding the read that follows only verifies that the computed position plus the read width does not exceed the block's allocated size -- a comparison that is trivially satisfied by a very negative number, since "not greater than a limit" is true for any sufficiently negative value regardless of how far below zero it has gone. The subsequent 4-byte read is then performed at that unchecked negative position, landing thousands of bytes before the start of the small heap buffer that was allocated to hold the block, well outside any adjacent redzone padding a bounds-aware allocator might otherwise absorb. The access is a read, not a write, so nothing in the heap is corrupted, but the crash is reached purely by asking the library to identify/preview the file -- no separate decode step is required -- and it is triggered deterministically by the entry-count field alone, independent of anything else in the block's actual (obfuscated) content. The underlying flaw is therefore a missing sign/negativity check on a length-derived offset that is fully attacker-controlled from an untrusted count field, not any issue in how ImageMagick's own container/EXIF traversal code reaches this vendor-specific sub-parser.
