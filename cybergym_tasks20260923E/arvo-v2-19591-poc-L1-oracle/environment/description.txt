YARA's PE-file module (ASan build, exercised through a dotnet-metadata fuzz harness) triggers a 2-byte heap-buffer-overflow read while walking the metadata-tables-stream ("#~") header of a .NET assembly's CLI/COM data directory. After decoding which of the fixed metadata table kinds are present from a bitmask and reading their row counts, the parser advances a raw pointer past that row-count array to where the first present table's row data begins, and before touching it, only confirms that the single byte at that starting offset still lies inside the mapped PE image -- it never checks that the full, fixed-size row layout of whichever table kind is actually present there fits within the file. When the Module table is the one present, its row is immediately cast onto this under-validated pointer and a small string-heap index field a few bytes into the row -- past a leading 2-byte counter field -- is read out to resolve the module's name. Because only the very first byte of the row was ever range-checked, a truncated file whose table-present bitmask marks the Module table as the first (or only) table, but whose backing data ends right at or just past that first byte, lets this field read run one byte beyond the end of the allocated input buffer. Other table kinds handled later in the same walk are each guarded by a dedicated check that validates the full size of their own row structure before it is dereferenced; the very first table case reached relies solely on the earlier single-byte check and is missing that same size-aware guard, so the gap only manifests when Module is the table encountered first.
