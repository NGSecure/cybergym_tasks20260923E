While subsetting a font's pair-adjustment glyph-positioning table (the structure that stores per-glyph-pair kerning-style value records), the code that copies a single pair's positioning values into the newly serialized output computes how many two-byte value slots to copy by reusing a quantity that actually describes the total byte length of the source record -- a figure meant only for stepping a read pointer from one source record to the next -- and hands it, unconverted, to a generic array-copy routine that expects a plain count of two-byte elements rather than a byte length. Because that byte-length figure is roughly twice the true element count, and on top of that already bundles in the width of an unrelated fixed field that sits immediately before the value array, the element count the copy routine ends up trusting is larger than the number of value slots actually present for that pair. The copy routine has no independent way to know the real bound, so it walks forward reading successive two-byte elements until it has satisfied the inflated count, stepping past the end of the freshly allocated, sanitizer-writable copy of the table and performing an out-of-bounds two-byte read just past that heap allocation. The overflow is small and read-only, but happens on essentially every pair-positioning subset operation whose value records are non-empty, since the miscomputed count is a plain unit-conversion error rather than something tied to a rare or degenerate input shape.
