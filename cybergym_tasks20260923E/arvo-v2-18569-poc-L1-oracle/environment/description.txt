A PKCS#15-style smart-card emulation layer for CoolKey-brand cards maintains a cache of on-card "objects", each keyed by an object identifier and populated on demand by issuing a card-read command that copies exactly as many bytes as the cache entry's own recorded size and allocates its backing buffer to that same size, so the entry's declared length and the size of the byte buffer actually behind it start out consistent. The card exposes two independent ways to enumerate these objects: a bulk "combined" listing that bundles several objects together with their data already attached, and a plain per-object directory listing that only reports an identifier plus a declared length, leaving the actual bytes to be fetched later. Nothing rejects the same object identifier from being registered a second time through the other listing mechanism, so a card can cause one identifier to end up with a small buffer already cached from the first listing while the same identifier's directory entry from the second listing carries a much larger declared length. When certificate data for a key object is later resolved, the code falls back to looking up a derived "certificate data" object by identifier and, without re-validating that the buffer already sitting behind that identifier actually holds as many bytes as the identifier's current declared length claims, allocates a destination buffer sized to that (now larger) declared length and copies that many bytes out of the still-small, already-cached source buffer. Because the copy trusts the newer, larger length value rather than the smaller size the buffer was originally filled at, the read walks far past the end of the small heap allocation. Reaching this code path only requires a card that answers the normal object-enumeration and object-read command sequence a real reader driver issues during card initialization, presenting the same object identifier with two different size claims across the two listing styles the driver already supports; no protocol-illegal or otherwise unrepresentable response is needed.
