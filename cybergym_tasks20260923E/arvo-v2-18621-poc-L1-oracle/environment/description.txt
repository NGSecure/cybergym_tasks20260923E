The crash surfaces while the library is only probing a camera raw image well enough to identify it, walking a TIFF-style container down through nested EXIF metadata until it reaches a proprietary, vendor-specific sub-block that is stored obfuscated and must be de-scrambled word-by-word before it can be read as plain metadata. The de-scrambling step advances an unsigned 32-bit read cursor through the block for a count of words that is taken from a size/length value recorded earlier in the same untrusted file rather than being clamped to how many bytes were actually allocated for that block; when a crafted, oversized count is supplied, the cursor keeps advancing past the true end of the small heap allocation that backs the block, and by the time the overflow is hit the resulting address is not merely a few bytes beyond the buffer but wildly out of range, consistent with the length-derived offset having grown into a value far larger than anything the allocation could have accommodated. The resulting access is a 4-byte read, not a write, so the immediate effect is an out-of-bounds load rather than heap corruption, but it happens deep inside third-party decoding logic that ImageMagick's raw-image coder delegates to and is reached purely by asking the library to identify/preview the file, with no separate opt-in decode step required. The underlying flaw is therefore a missing bounds check on a length field that is fully attacker-controlled and used directly to drive how far a decryption loop walks into a fixed-size metadata buffer, rather than any issue in ImageMagick's own container/EXIF traversal code that gets it to that point.
