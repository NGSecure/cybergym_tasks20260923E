This crash is reached through the library's full document-rewriting path, not through a bare image-decoding entry point: a deliberately malformed PDF file is parsed (its cross-reference table is missing and gets reconstructed heuristically, and several objects have to be patched up during parsing), and one of its objects carries an embedded JPEG-compressed image stream that is itself corrupt near its very start, forcing the JPEG decoder to skip past extraneous bytes before it can recover a valid marker and continue. When the tool goes on to re-emit the document, it takes the path where the already-compressed image data is copied through largely unchanged rather than being re-encoded: the writer buffers the bytes of the re-serialized object internally so it can compute and prepend the correct length header before actually emitting the object, and it is that internal buffering/length-finalization step -- a step that happens strictly after the image has finished decoding, not during the decode itself -- that ends up reading from a large sample-array heap block the JPEG decoder had allocated for the image's rows. The sanitizer flags memory it still regards as unwritten at the point that finalization step reads it, even though decoding had already completed by then; the defining characteristic here is that the failure surfaces one step downstream of decoding, at the point where the raw decoded/passthrough bytes are collected and measured for re-emission, rather than inside the decoder itself.
