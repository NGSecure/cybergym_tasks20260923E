This is a heap out-of-bounds read in the driver that decodes a security-token vendor's proprietary object format inside opensc's smart-card enumeration path. As the driver walks the token's object directory, it appends every object entry it sees to an in-memory table keyed by a 4-byte identifier the token supplies -- nothing rejects a second entry that reuses an identifier already present in the table, even if that second entry declares a different byte length than the first. The first time any entry for a given identifier is actually read from the token, the driver allocates a buffer sized to exactly that entry's own declared length, fills it with the bytes read back, and then stores the resulting pointer on whichever table entry a plain identifier lookup happens to return -- not necessarily the specific entry that triggered the read. When two entries share one identifier with different declared lengths, that lookup can resolve to either of them, so the buffer ends up attached to a table entry whose own recorded length disagrees with the buffer's true allocated size. A later, unrelated attribute fetch for that same identifier finds the entry already has data cached and skips allocating anything fresh, instead trusting the entry's own (possibly larger) declared length as the true size of the buffer it inherited. When it then walks that object's attribute records looking for one attribute it can't find among the regular records, it falls back to reading a small fixed-position field near the start of the object header directly, believing the trusted (but wrong) length guarantees there's room -- and reads a few bytes past the end of the real, much smaller allocation. Because the token's whole object directory and object payloads are attacker/fuzzer-supplied bytes with no cryptographic integrity check at this layer, producing two internally-plausible, individually well-formed directory entries that happen to share an identifier but disagree on length is entirely sufficient to reach this state; no protocol-illegal response is required.
