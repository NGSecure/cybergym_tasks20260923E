This crash occurs while the image library renders vector-drawing primitives parsed from an embedded drawing-language stream, specifically during the stage where a stroked polygon outline (including dashed strokes) is expanded into a list of coordinate points that will later be filled and rendered. To hold this expanding point list, the routine keeps two parallel dynamically-allocated point arrays and tracks a running capacity counter; before tracing begins, it computes an initial capacity as roughly twice the number of input vertices plus a fixed constant reserve meant to absorb the extra points appended for line joins, caps, and curve subdivisions that a bare vertex count would not predict, and the very first allocation for both arrays is sized to include that reserve. As the outline is traced, the capacity counter is checked before each batch of new points is appended, and whenever the next batch would not fit, the counter is incremented by exactly the size of that batch and both arrays are reallocated to hold precisely that many points, no more. The defect is that the fixed constant reserve baked into the initial allocation is a one-time bonus that is never re-added on any later growth step, so once even a single reallocation happens the arrays only ever contain just enough room for the points explicitly accounted for by the capacity counter, with none of the extra slack the initial sizing assumed would always be present. Some code paths append a handful of fixed, uncounted extra points after the last explicit capacity check for a given segment, implicitly relying on that constant reserve still being available; once the arrays have already grown past their initial size, that reserve is gone, and such uncounted appends write one or more coordinate points past the end of the freshly reallocated heap buffer, corrupting adjacent heap metadata. A crafted drawing command with enough vertices or curve segments to force at least one buffer growth, followed by one of these uncounted point appends, drives the write index past the newly (but insufficiently) resized allocation and crashes the process with an out-of-bounds heap write. The fix restores the constant reserve on every allocation and every subsequent growth step, not only the first one, so the arrays always retain the same safety margin the uncounted append sites depend on regardless of how many times they have already been resized.
