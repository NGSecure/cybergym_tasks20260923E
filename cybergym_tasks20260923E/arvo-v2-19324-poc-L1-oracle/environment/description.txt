When nDPI performs protocol detection on UDP-carried memcached traffic, it first skips a fixed-length UDP request header and then, starting from the position after the skip, compares the payload prefix against a set of known memcached command/response keyword constants one by one via fixed-length string comparisons; each comparison is preceded by a guard that checks a "remaining available bytes" variable against the keyword's length (skipping the comparison if the keyword is longer). Root cause: this "remaining available bytes" value is computed only once, at function entry, from the total UDP payload length, and is never decremented by the header length after the header is skipped and the read pointer advanced -- so the guard actually operates on the larger, pre-skip total length. When a UDP payload's total length just barely satisfies the "header + shortest response" lower-bound check, but the actual number of bytes remaining after the header is skipped is shorter than one of the longer keywords, the guard still passes using the un-decremented total length, letting the subsequent string-comparison routine read past the end of the payload buffer.
