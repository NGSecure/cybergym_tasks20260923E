YARA's rule compiler (libyara), exercised through a fuzz harness that repeatedly feeds candidate rule-text strings into a single long-lived compiler instance and only tears that instance down afterward: a use of uninitialized (already-released) heap memory occurs while the compiler object is finally being cleaned up. Root cause: when parsing a rule whose condition contains a `for`-loop expression, if the parser hits a syntax error inside or immediately after that loop -- especially when for-loops are nested -- the error-recovery code responsible for releasing the heap-allocated identifier strings of the loop's iteration variables only unwinds and frees the innermost active nesting level. It decrements the loop-nesting depth without freeing the variable bookkeeping for any outer loop level still on the stack, and even for the level it does clean up it frees each variable's identifier string without also resetting that level's recorded variable count or clearing the now-dangling pointers. Because the compiler instance is reused for further rule text within the same run, this leaves inconsistent per-loop state -- a nonzero variable count paired with pointers into memory that has already been released -- sitting inside the compiler's internal loop-context array. That stale bookkeeping is not touched again until the compiler is ultimately destroyed, at which point it gets walked once more and the already-freed memory is read as though it still held valid content.
