The crash surfaces while the library is only probing a camera raw image well enough to identify it, walking a TIFF-style container down through nested EXIF metadata until it recognizes, from the maker/model strings recorded earlier in the same file, that it is looking at a particular vendor's proprietary sub-block; that recognition alone, with no further validation, is enough to hand control to a dedicated parser for that vendor's obfuscated metadata format. After locating and decrypting one section of that block, the parser reads a small directory of fixed-width entries out of it in a loop: a 16-bit entry count is read first, and then a cursor is advanced twelve bytes at a time, once per entry, reading a handful of small fixed-offset fields -- an identifier, a type, a couple of 4-byte values -- out of each entry before moving the cursor to the next one. Before this loop begins, the code does perform a bounds check meant to guard the reads that happen inside it, but the check computes its limit from a position that was fixed once, before the loop started, rather than from the cursor that is actually being advanced and read from on every iteration; the two are equal only for the very first entry. As the loop advances through successive entries the read cursor keeps moving forward while the value the bounds check re-derives its limit from never changes, so the same comparison -- which was accurate for entry zero -- is silently reused, unchanged, for every later entry regardless of how far the cursor has actually traveled. When the entry count read from the file is large enough that the last entries' cursor position runs past the true end of the block's small heap allocation, nothing catches it, because the guard is still only re-confirming that the very first entry was in bounds. The resulting 4-byte read on one of those late-loop fields lands just one byte past the end of the allocated block -- a tight, exact overrun rather than a wild one, consistent with the loop stepping cleanly off the end of the buffer by design of the entry layout rather than jumping to an arbitrary address. The access is a read, not a write, and is reached purely by asking the library to identify/preview the file, with no separate decode step required; it is driven entirely by how large an entry count the crafted file declares for this directory, independent of the actual (obfuscated) values the entries contain. The underlying flaw is therefore a bounds check that validates the wrong variable -- a loop-invariant position instead of the position that actually advances and gets dereferenced each iteration -- rather than any issue in how ImageMagick's own container/EXIF traversal code reaches this vendor-specific sub-parser.
