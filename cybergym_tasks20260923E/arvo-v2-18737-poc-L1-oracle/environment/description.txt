This is a heap out-of-bounds read in nDPI's STUN protocol dissector, triggered while it extracts a text-style attribute (such as a server/user name) from an incoming STUN message. The parser reads a length value out of the attribute header and uses it, together with a running read offset into the packet's payload buffer, to drive a byte-by-byte copy loop that fills a fixed-size per-flow output buffer; that destination buffer is zeroed before the copy starts and is large enough, so the defect is not on the write side. The loop's only bound is the attacker-supplied attribute length itself: before the first byte is copied, nothing checks whether that many bytes are actually still present between the current read offset and the true end of the packet's payload allocation. A crafted STUN message can declare an attribute length larger than what genuinely remains after the current offset, so as the loop keeps incrementing the source read pointer it walks straight past the end of the heap buffer backing the payload, and the read that finally lands beyond the allocation is what triggers the crash. The direction of the bug matters: it is the declared length growing beyond the real remaining input, not some degenerate small value slipping past an existing check, and the missing guard is a comparison of the current offset-plus-copy-count against the packet's true payload length, not any bound on the destination buffer's capacity.
