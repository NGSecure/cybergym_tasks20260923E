While subsetting a chained contextual rule, the subsetting logic re-validates the rule's trailing backtracking, input, and lookahead glyph-id lists against the retained glyph set before copying the rule forward. To locate the second and third of these three variable-length lists inside the rule's own backing bytes, the check uses a position baked in from the record's compile-time layout instead of walking forward from the first list using its actual, data-dependent length; whenever that first list is non-empty the assumed position undershoots where the later lists really start, so the validation step ends up interpreting unrelated bytes elsewhere in the table as if they were a list's entry count and glyph values. The miscomputed count itself still lands inside the small heap allocation holding the font table, so it is read successfully, but walking through that many "entries" from the wrong starting point drives the read pointer past the end of the allocation partway through, and it is the fetch of one particular glyph-id value -- during the pass that checks each entry for membership in the retained glyph set -- that lands two bytes beyond the buffer and triggers the out-of-bounds read.
