In the FLAC reference encoder (ASan build), the sample-ingest entry points never validate that the caller-supplied PCM values actually fit within the bit depth the encoder session was configured for. Internally, once samples are copied into the encoder's per-channel working buffers, later stages (choosing how to decorrelate/pack each channel's samples and sizing the intermediate representations used for that) implicitly trust that every sample's magnitude is bounded by that configured bit depth rather than checking the values themselves. Feeding the encoder one or more samples whose magnitude exceeds what the configured bit depth can represent violates that assumption, and the resulting arithmetic drives an internal write past the extent an allocation was sized for, quietly corrupting the heap allocator's bookkeeping for a nearby chunk. Nothing observable happens at that moment. The corruption only surfaces much later, when the stream is finalized and the encoder releases its low-level bit-packing output buffer as part of normal teardown: freeing that buffer requires the allocator to update the corrupted chunk metadata, and doing so computes a garbage address, so the crash presents as a wild write inside the sanitizer's own allocator bookkeeping at a routine, otherwise-unremarkable free() call -- physically far from, and unrelated in appearance to, the out-of-range-sample write that actually caused it.
