While reassembling a TLS server certificate for its fingerprint calculation, nDPI carries per-flow state across packets: a count of certificate bytes still owed to the running hash, and the byte offset within the next packet's payload where those bytes are expected to continue. When a new packet arrives, the code computes how many bytes of that packet are usable by subtracting the remembered offset from the packet's payload length, using ordinary unsigned integer arithmetic and without first verifying that the payload is actually longer than the offset; if the two packets don't line up as expected — a shorter follow-up segment, or state left over from a differently-shaped earlier record — that subtraction underflows into an enormous value, and the outstanding-byte counter (itself derived from an attacker-supplied certificate-length field) ends up governing how many bytes are handed to nDPI's generic incremental hashing helper instead of the true amount of data available. On this input, the hashing helper's very first step — an unconditional copy meant to top off its internal 64-byte working block from the caller-supplied data — trusts that count and reads straight past the tail of the small, freshly allocated packet buffer, producing an out-of-bounds heap read before a single byte of the intended certificate data is legitimately available.
