This proof-of-concept is a malformed HDF5-based MAT file that trips a different bug than the two related local-heap-corruption crashes in this same reader family: rather than corrupting the group directory's free-list bookkeeping, it plants a bad length value inside a fixed-size metadata record attached to one of the file's stored variables, a record that describes what default bytes should be used to pad any unwritten elements of that variable. As the reader opens the variable and works through the small header of records that accompany it, it reaches this padding-default record, reads the length field the record itself declares, and uses that attacker-controlled length to size a copy of the record's payload into a buffer it already allocated based on the expected, fixed layout of that record type -- without checking the declared length against the buffer's actual size before copying. Because the length embedded in the crafted record is much larger than what the destination buffer was sized for, the copy reads far past the end of the small allocation backing it, producing a wild out-of-bounds read. This happens while the reader is still building up a single variable's in-memory description, immediately after successfully locating that variable by name during directory enumeration, so it requires the surrounding directory structure to be intact enough to reach that variable but only a single downstream metadata record's length field to be corrupted for the crash to fire.
