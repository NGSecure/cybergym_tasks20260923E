libavc's H.264 decoder (ASan build, avc_dec_fuzzer harness): when a new slice starts, the decoder checks whether the previous picture was left with only one field decoded (a "dangling" field) so it can properly close that picture out before beginning a new one, but the check only fires when the new slice's frame_num differs from the still-open field's frame_num. It misses the case where a slice belonging to a new, full-frame (non-field) picture reuses the same frame_num as the pending field. In that case the decoder wrongly keeps treating it as a continuation of the old picture instead of starting a fresh one, so its accounting of how many slices the picture actually contains ends up out of sync with a fixed-size per-picture slice-tracking array that libavc allocates with exactly one entry per macroblock in the picture. The picture's multi-threaded slice-decode worker then walks one entry past the end of that array, producing a heap-buffer-overflow read.
